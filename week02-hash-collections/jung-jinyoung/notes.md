# 2주차 학습 정리 — 정진영

## 1. 핵심 질문 답변

> 검색한 문장을 붙여넣지 말 것. 본인 문장으로 쓰고, 예시 코드를 곁들이면 좋음.

### Q1.`equals`만 재정의하고 `hashCode`는 그대로 두면, 그 객체를 `HashMap` 키로 썼을 때 무슨 일이 벌어지는가?

hashCode를 염두에 두지 않고 equals만 재정의한다면, 프로그램이 의도한 대로 동작하지 않을 가능성이 있다.

Objcet.hashCode()는 객체의 정체성 기반 값을 리턴하는데, "equals"가 같으면 "hashCode"도 같아야 한다는 상태가 깨지게 되기 때문이다.

HashMap.get()의 순서는 'hashCode로 버킷 인덱스 결정' -> '그 버킷안에서 equals 비교'로 진행된다. 첫 단계에서 이미 의도한 동작대로 저장되지 않는, 예를 들어 다른 버킷으로 저장이 된다면 equals는 호출되지 못한다.

그래서 equals와 hashCode는 항상 같은 필드를 기준으로 함께 재정의해야한다.

### Q2.`HashMap` 키로 **가변 객체**를 쓰면 안 되는 이유는? (필드를 바꾸면 어떻게 되는가)

데이터를 추가한 이후에 키의 필드가 바뀌면 hashCode가 달라져 저장된 값을 찾을 수 없게 된다.

HashMap은 보관 중인 키 객체를 감시하지 않기 대문에, 필드가 바뀌어도 알 수 있는 방법이 없다.

### Q3.모든 키의 `hashCode`가 같다면 조회 시간복잡도는 어떻게 되는가? 자바 8 이후에는?

O(n) -> 자바 8 이후에는 O(log n)

hashCode가 같다면 저장될 버킷 인덱스도 전부 같기 때문에 n개의 데이터가 하나의 인덱스에 체이닝되어 저장된다.

조회시 버킷을 앞에서부터 순차 비교 하기 때문에, 해시맵이지만 실질적으로 연결 리스트 형태가 되어 버린다.

자바 8 이후에는 트리화와 리사이징이 도입되어 log n으로 시도할 수 있게 된다. 리사이징을 먼저 시도하고, 배열 크기가 너무 커지는 것을 방지하기 위해 이후 트리화가 진행된다.

## 3. 구현 과제 회고

> 구현 과제 위치 : [MyHashMap.java](./src/MyHashMap.java)

- 어떻게 설계했는가
  1. 제네릭 없이 키는 String, 값은 int로 고정 - 원래 요구사항은 제네릭이지만, 제네릭 배열을 만들 수 없어 캐스팅이 필요했고 그게 지금 이해 범위 밖이라 뺐다.
  2. 버킷 배열 크기 16, 인덱스는 Math.abs(key.hashCode() % table.length)
  3. 충돌 처리 없이 덮어쓰기로 시작 — 충돌이 실제로 어떤 결과를 내는지 먼저 보려고

- 막혔던 지점:
  1. 제네릭 배열 생성 : 컴파일 에러 & 자주 해보지 못한 패턴 -> 포기하고 단순화

- JDK 실제 구현과 비교했을 때 다른 점
  1. 내 구현 코드는 Math...로 나머지 연산을 하지만 JDK는 (n - 1) & hash로 비트 연산 : 배열 크기를 항상 2의 거듭제곱으로 유지하기 때문에 가능한 방식이고, 나머지 연산보다 빠름
  2. 현재 구현 단계에서 충돌 처리가 안되어 있지만, JDK는 next로 노드를 연결하고 체이닝 처리 후 트리화 진행
