## 2. HashMap 내부

> 리스트
> - 버킷 배열 + 해시 함수 + 인덱스 계산
> - 충돌 처리: **체이닝(연결 리스트)**
> - 로드 팩터(0.75)와 리사이징 시점
> - 자바 8 이후 **버킷 트리화**(연결 리스트 → 레드-블랙 트리) 조건

### 1. 버킷 배열, 해시 함수, 인덱스 

`Arraylist`로 특정 단어의 위치를 찾아야하는 코드를 작성해보면 아래와 같다.
```java
List<String> words = new ArrayList<>();
int idx = words.indexOf(word); // 앞에서 하나씩 비교 -> O(n)
```
만약 찾아야할 단어 개수가 10만개면 최악의 경우 10만 x 10만 = 100억번 비교.  
"값"의 "위치"를 바로 계산해야 할 필요성이 있다. 

- 버킷 배열 : `Node[] table` 형태로 데이터가 실제로 저장되는 장소
- 해시 함수 : `hashcode()` 메서드로, 키값을 정수 하나로 변환
- 인덱스 계산 : 해당 정수를 배열의 길이로 나머지 연산하여 위치 특정 

즉 전체의 흐름은 아래와 같다. 
```
키 ──hashCode()──▶ 정수 ──▶ table.length──▶ 인덱스 ──▶ table[인덱스]
     해시 함수                인덱스 계산                버킷 배열
```

왜 배열의 형태인가 생각해보면, 배열은 인덱스만 알면 바로 접근하는 O(1)의 복잡도를 가졌기 때문이다.

### 2. 충돌 처리 : 체이닝 (연결 리스트)
만약 크기가 고정된 배열 칸 하나(버킷)에 데이터가 하나만 들어간다는 규칙이라면,  
이미 저장된 데이터 위치에 다른 값이 저장되면 기존 데이터가 밀려 지워져버리게 된다.

이런 충돌 처리를 하는 방법 중 하나가 바로 체이닝, 즉 연결 리스트 형태로 해당 위치에 줄을 세우는 방식이다.

```
// 예시 : 11번 위치에 값이 계속 추가 되는 경우
table[11] → n1 → n2 → n3 → ... → n100
```

만약 위의 예시 처럼 100개의 데이터가 하나의 위치에 몰리면, 값을 찾기 위해서는 최악의 경우 100번 비교해야 한다.  
그렇게 되면 사실상 ArrayList와 다를 게 없는 O(n)이 되는 약점이 있다.


<hr/>

### 3. 로드 팩터(0.75)와 리사이징 시점

체이닝의 약점에서 본 것 처럼 한 칸에 데이터가 너무 많이 몰리면 O(n)이 된다. 
그렇다면 칸 개수 자체를 늘려 충돌을 피할 수 있는데, 이 때 어떤 기준으로 배열을 늘릴 수 있는지가 필요하다.

그 기준값을 로드 팩터라고 하고 0.75는 75% 칸이 찼을 때 미리 배열을 2배로 늘린다는 뜻이다.

버킷 배열의 기본 칸 개수는 16개이고, 로드팩터가 0.75일 때 데이터가 12개가 넘는 순간 
칸 개수를 32배로 확장하고, 이 과정을 resize라고 한다.


<hr />

### 4.자바 8 이후 **버킷 트리화**(연결 리스트 → 레드-블랙 트리) 조건

하지만 로드 팩터로 리사이징한다 해도 한 칸에만 데이터가 유난히 많이 몰릴 수 있다. 
이때 줄 자체의 구조를 바꿔서 빠르게 만드는 방법이 바로 연결 리스트 구조를 레드-블랙트리 구조로 바꾸는 것이다.  

레드-블랙 트리 구조로 트리가 한쪽으로 쏠리지 않게 새 데이터가 들어와도 트리가 균형을 잡으며  
항상 `log n`속도를 보장해주기 때문에 한 칸에 데이터가 많이 몰려도 탐색 속도를 `log n`으로 잡을 수 있다.
