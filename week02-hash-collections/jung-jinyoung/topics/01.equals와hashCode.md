## 1. equals / hashCode 계약

### Object.equals 의 5가지 규약

`Object.equals`는 값이 아니라 참조를 본다. 즉 주소값을 보는 것인데, JDK 실제 구현은 아래와 같다.

```java
    public boolean equals(Object obj) {
        return (this == obj);
    }
```

코드를 보면 재정의하지 않은 equals는 `==`와 동일하게 동작한다. 즉, 두 참조가 메모리 상에서 같은 객체를 가리키는 경우에만 `true`를 반환한다.

하지만 기본 equals로는 비교가 안 되는 상황이 있다. 예를 들어 `Point(1,2)`와 `Point(1,2)`처럼 `new`로 따로 만든 두 객체는 참조가 달라 기본 equals로는 항상 false다. 
하지만 실제로 필요한 건 "값이 같은가"이지 "같은 객체인가"가 아니다. 

그래서 값 비교가 필요한 클래스(좌표, 학생 정보 등)는 "같다"의 기준을 직접 재정의한다.

모든 클래스에서 해당 `Object.equals`를 상속받기 때문에, 필요에 따라 재정의하여 "같다"의 기준을 직접 정할 수 있다.

equals를 재정의 하는 경우에도 지켜야 할 5가지 규약이 있는데,  
컬렉션(List, Set, Map 등)이 내부적으로 equals를 호출할 때 어떤 클래스든 최소한 이렇게는 동작할 거라는 전제를 깔고 짜여 있기 때문이다. 
이 전제가 규약이며, 어기면 컴파일 에러 없이 조용히 틀린 결과가 나온다.

1. 반사성(reflexivity)  
   null이 아닌 모든 참조 값 x에 대해 x.equals(x)를 만족해야 한다. 단순히 말하면 객체는 자기 자신과 비교했을 때 같아야 한다는 뜻이다.  
   만약에 성립되지 않는다면, contain 메서드를 활용한 객체 찾기가 불가능해지게 될 것이다.   
   <br>
2. 대칭성(symmetry)   
   null이 아닌 모든 참조 값 x, y에 대해 x.equals(y)=true => y.equals(x)=true 가 성립되어야 한다.  
   컬렉션 내부에서 a.equals(b)로 짤지 b.equals(a)로 짤지는 구현자 마음이라, 대칭성이 없으면 호출 순서에 따라 결과가 달라지는 재현 불가능한 버그가 생긴다.   
   <br>

3. 추이성(transitivity)  
   null이 아닌 모든 참조 값 x, y, z에 대해 x.equals(y)=true 이고 y.equals(z)=true 이면 x.equals(z)=true 여야 한다.

   값 클래스를 상속으로 확장하면서 새로운 필드를 추가하면 깨지기 쉽다.
   
   예: Point(x, y)를 상속해 ColorPoint(x, y, color)를 만들었다고 하자.
   - red = ColorPoint(1,2,RED), p = Point(1,2), blue = ColorPoint(1,2,BLUE)
     - red.equals(p) → true (Point 기준으로 비교하면 좌표만 봄)
     - p.equals(blue) → true (마찬가지로 좌표만 봄)
     - red.equals(blue) → false (색깔이 다름)

   red=p, p=blue인데 red≠blue이므로 위반. 상위 타입과 비교할 때 새 필드(color)를 무시하는 순간, 상위 타입이 서로 다른 두 하위 객체를 몰래 같다고 이어붙이는 우회 경로가 된다. <br/>
   
   **왜 이게 문제인가**: "같다"는 원소들을 그룹으로 묶는 관계(동치 관계)여야 한다. 추이성이 깨지면 HashSet 같은 컬렉션에서 그룹핑 자체가 모순된다. 예를 들어 red와 blue를 각각 넣으면 서로 다른 원소로 등록되는데, p를 넣으면 red와도 같고 blue와도 같다고 판정될 수 있다. 서로 다르다고 확정된 두 그룹 모두에 걸치는 모순이 생기고, 어떤 걸 대표로 남길지조차 정의 불가능해진다.

<br>

4. 일관성(consistency)  
   null이 아닌 모든 참조 값 x, y에 대해, 두 객체가 변경되지 않는 한 x.equals(y)를 여러 번 호출해도 항상 같은 결과가 나와야 한다.  
   equals 비교에 사용하는 필드가 가변(mutable)이면 깨질 수 있다. 그래서 equals에 쓰는 필드는 final로 두는 것이 관용적이다. (예: java.net.URL.equals는 네트워크 상태에 따라 결과가 달라져 이 규약을 위반한 사례로 유명하다.)
   <br>

5. null-아님 (non-nullity)  
   null이 아닌 모든 참조 값 x에 대해 x.equals(null)은 false여야 한다. NullPointerException을 던지는 것도 위반이다.  

<br>

반대로, 재정의하지 않는 게 좋은 경우가 있다. (재정의가 필요한 이유와 반대 상황)    
모든 클래스가 재정의를 필요로 하는 것은 아니다.   
값 비교 자체가 의미 없는 클래스라면 재정의할 이유가 없으며, 아래의 조건에 해당되는 경우 재정의는 불필요하다.

<br> 

- 각 인스턴스가 본질적으로 고유하다 - `Thread` 등, 비교할 "값" 자체가 없음
- 논리적 동일성을 검사할 일이 없다 - `Random` 등, 값은 있지만 비교할 이유가 없음
- 상위 클래스의 equals가 하위 클래스에도 들어맞는다 - 새 필드를 추가하지 않은 경우
- private/package-private 클래스이고, equals가 호출될 일이 없다.
- 인스턴스 통제로 값마다 객체가 하나만 존재한다 - `enum` 등. 값이 같으면 반드시  같은 객체이므로 참조 비교만으로 충분
