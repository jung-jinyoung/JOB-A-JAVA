# 자바 제네릭

## 1. 제네릭을 사용하는 이유

제네릭은 클래스나 인터페이스의 구조와 동작은 같지만 다루는 데이터 타입이 달라질 때 사용한다.

```java
List<String> names;
List<Integer> scores;
List<Student> students;
```

하나의 `List` 구조를 여러 타입에 재사용하면서, 잘못된 타입이 들어오는 것을 컴파일 시점에 막을 수 있다.

```java
List<String> languages =
    new ArrayList<>();

languages.add("Java"); // 가능
languages.add(100);    // 컴파일 에러
```

값을 꺼낼 때도 직접 형 변환할 필요가 없다.

```java
String language = languages.get(0);
```

제네릭의 주요 목적은 다음과 같다.

- 하나의 코드로 여러 타입 처리
- 컴파일 시점의 타입 검사
- 불필요한 형 변환 제거
- 실행 중 `ClassCastExceptionException` 발생 가능성 감소

## 2. 제네릭이 없다면

제네릭 없이 `Object`로 모든 값을 처리하면 서로 다른 타입이 섞일 수 있다.

```java
List values = new ArrayList();

values.add("Java");
values.add(100);
```

값을 꺼낼 때 직접 형 변환해야 한다.

```java
String language =
    (String) values.get(0);
```

잘못된 객체를 문자열로 변환하면 실행 중 `ClassCastException`이 발생한다.

```java
String language =
    (String) values.get(1);
```

## 3. 제네릭 불공변성

`String`은 `Object`의 하위 타입이다.

```java
Object value = "Java";
```

하지만 `List<String>`은 `List<Object>`의 하위 타입이 아니다.

```java
List<String> strings =
    new ArrayList<>();

List<Object> objects = strings; // 컴파일 에러
```

이를 허용하면 `objects`를 통해 정수 같은 다른 타입을 넣을 수 있다.

```java
objects.add(100);
```

그러면 문자열만 들어 있어야 하는 `strings`의 타입 안전성이 깨진다.

> `String`이 `Object`의 하위 타입이어도 `List<String>`은 `List<Object>`의 하위 타입이 아니다.

## 4. extends와 super

### `? extends T`

```java
List<? extends Number> values
```

정확한 타입은 모르지만 `Number` 또는 그 하위 타입을 담은 리스트다.

```java
List<Integer>
List<Double>
List<Long>
```

값을 `Number`로 안전하게 꺼낼 수 있다.

```java
Number value = values.get(0);
```

하지만 실제 리스트 타입을 모르므로 구체적인 값을 추가할 수 없다.

```java
values.add(10); // 컴파일 에러
```

### `? super T`

```java
List<? super Integer> values
```

`Integer` 또는 그 상위 타입을 담는 리스트다.

```java
List<Integer>
List<Number>
List<Object>
```

`Integer`를 안전하게 추가할 수 있다.

```java
values.add(10);
```

꺼낼 때 정확한 타입은 보장할 수 없으므로 `Object`로 받아야 한다.

```java
Object value = values.get(0);
```

## 5. PECS

PECS는 다음 문장의 약자다.

```text
Producer Extends, Consumer Super
```

메서드 관점에서 리스트가 값을 제공하면 생산자다.

```java
List<? extends T> source
```

메서드가 리스트에 값을 넣으면 리스트는 소비자다.

```java
List<? super T> destination
```

```java
static <T> void copy(
    List<? extends T> source,
    List<? super T> destination
) {
    for (T value : source) {
        destination.add(value);
    }
}
```

```text
source에서 값을 꺼냄
→ Producer
→ extends

destination에 값을 넣음
→ Consumer
→ super
```

## 6. 타입 소거

제네릭은 Java 5에서 기존 코드 및 JVM과의 호환성을 유지하며 추가되었다.

제네릭 타입은 주로 컴파일 시점의 타입 검사에 사용되고, 컴파일 후에는 구체적인 타입 인자의 일부가 제거된다. 이를 타입 소거라고 한다.

```java
class Box<T> {
    private T value;

    void set(T value) {
        this.value = value;
    }

    T get() {
        return value;
    }
}
```

제한 없는 `T`는 컴파일 후 개념적으로 `Object`로 처리된다.

```java
class Box {
    private Object value;

    void set(Object value) {
        this.value = value;
    }

    Object get() {
        return value;
    }
}
```

컴파일러는 값을 꺼내는 위치에 필요한 형 변환을 추가한다.

```java
String value = box.get();
```

개념적으로:

```java
String value = (String) box.get();
```

실제 저장된 문자열 객체가 일반 `Object` 객체로 변하는 것은 아니다. 필드의 코드상 타입이 `Object`로 처리될 뿐 실제 객체는 계속 `String`이다.

## 7. `new T[]`가 불가능한 이유

자바 배열은 실행 시점에도 실제 원소 타입을 알고 검사한다.

```java
String[] strings = new String[3];
Object[] objects = strings;

objects[0] = 100; // ArrayStoreException
```

실제 배열이 `String[]`이라는 것을 JVM이 알고 있기 때문에 정수 저장을 막는다.

하지만 제네릭의 `T`는 타입 소거 후 구체적인 타입을 알 수 없다.

```java
class Box<T> {
    private T[] values;

    Box(int size) {
        values = new T[size]; // 컴파일 에러
    }
}
```

```text
배열은 실행 시 원소 타입 필요
제네릭 T는 실행 시 구체적인 타입이 소거됨
→ 안전한 배열 타입을 만들 수 없음
```

따라서 자바는 `new T[]`를 허용하지 않는다. 배열이 꼭 필요하지 않다면 보통 `List<T>`를 사용한다.

## 아직 모르겠는 것

타입 소거가 기존 자바 코드와 JVM의 호환성을 위해 사용된다는 배경은 이해했다. 다만 `Box<String>` 코드가 컴파일 과정에서 타입 검사, 타입 소거, 자동 형 변환을 거쳐 실행되는 전체 흐름을 명확하게 설명하는 것은 아직 어렵다.
