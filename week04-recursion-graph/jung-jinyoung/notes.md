# 4주차 학습 정리 — 정진영

## 1. 핵심 질문 답변

### Q1. 재귀 깊이 한계는 무엇이 결정하는가? 100만 깊이 재귀가 필요하면 어떻게 해야 하는가?

재귀 호출이 일어날 때마다 JVM 스택에 새로운 스택 프레임이 쌓인다. 따라서 재귀 깊이의 한계는 하나의 고정된 숫자가 아니라 다음 요소에 따라 달라진다.

- 각 스레드에 할당된 스택 크기
- 메서드 호출 한 번에 필요한 스택 프레임의 크기
- JVM과 실행 환경
- JVM 스택 크기를 설정하는 `-Xss` 옵션

스택 공간이 부족해지면 `StackOverflowError`가 발생한다. `-Xss` 값을 늘리면 한계를 늦출 수는 있지만, 100만 깊이처럼 매우 깊은 재귀를 안전하게 처리하는 근본적인 해결책은 아니다. 또한 자바는 꼬리 재귀 최적화를 보장하지 않으므로 꼬리 재귀로 작성해도 호출 프레임이 계속 쌓일 수 있다.

따라서 100만 깊이의 처리가 필요하다면 반복문으로 바꾸는 것이 안전하다. DFS처럼 이전 상태를 기억해야 한다면 JVM의 호출 스택 대신 `ArrayDeque`를 명시적인 스택으로 사용한다.

```java
Deque<Integer> stack = new ArrayDeque<>();
stack.push(start);

while (!stack.isEmpty()) {
    int current = stack.pop();
    // current 처리
}
```

### Q2. 인접 행렬 대신 인접 리스트를 쓰는 기준은 무엇인가?

정점 수를 `V`, 간선 수를 `E`라고 하면 인접 행렬은 `V × V` 공간을 항상 사용하므로 공간복잡도가 `O(V²)`이다. 반면 인접 리스트는 실제로 존재하는 간선만 저장하므로 `O(V + E)` 공간을 사용한다.

| 기준                     | 인접 행렬   | 인접 리스트 |
| ------------------------ | ----------- | ----------- |
| 저장 공간                | `O(V²)`     | `O(V + E)`  |
| 두 정점의 연결 확인      | `O(1)`      | `O(deg(u))` |
| 한 정점의 모든 이웃 탐색 | `O(V)`      | `O(deg(u))` |
| 적합한 그래프            | 밀집 그래프 | 희소 그래프 |

`E`가 `V²`에 비해 매우 작고, DFS나 BFS처럼 실제 이웃을 따라 탐색하는 경우에는 인접 리스트가 적합하다. 반대로 대부분의 정점이 서로 연결되어 있고 두 정점의 연결 여부를 자주 확인해야 한다면 인접 행렬을 고려할 수 있다.

무조건 정점과 간선의 개수만 보는 것이 아니라, 필요한 연산이 연결 여부 확인인지 이웃 전체 탐색인지도 함께 판단해야 한다.

### Q3. 스트림이 일반 for문보다 느려지는 상황을 하나 들고, 왜 그런지 설명하라.

짧은 `List<Integer>`의 합계를 구하는 것처럼 데이터가 적고 계산이 단순한 경우에는 스트림이 일반 `for`문보다 느릴 수 있다.

```java
int sum = numbers.stream()
        .mapToInt(Integer::intValue)
        .sum();
```

스트림은 처리 파이프라인을 만들고 람다를 연결하고 호출하는 추가 비용이 있다. `Stream<Integer>`로 숫자를 처리하면 `int`와 `Integer` 사이의 박싱과 언박싱 비용도 발생할 수 있다. 계산 자체가 단순하거나 데이터가 적다면 이 부가 비용의 비중이 커진다.

숫자 계산에서는 `IntStream` 같은 기본형 특화 스트림으로 박싱 비용을 줄일 수 있다. 하지만 반복문과 스트림 중 어느 쪽이 빠른지는 실행 환경과 데이터 크기에 따라 달라지므로, 성능이 중요한 부분은 실제로 측정해야 한다.

> 구현 과제: [Graph.java](./src/Graph.java)

### 어떻게 설계했는가

기존 그래프라는 구조랑 dfs, bfs 같은 탐색 방법을 알고 있었기 때문에 구현하는데 큰 어려움은 없었습니당~ 그래도 자바로 새롭게 구현해보니까 꼼꼼하게 다시 복습할 수 있어서 좋았습니다!

- 생성자에서 정점 수와 방향 그래프 여부를 받아 그래프의 기본 구조를 결정했다.
- 각 정점의 이웃만 저장하도록 `List<List<Integer>>` 기반의 인접 리스트를 사용했다.
- `addEdge(int u, int v)`는 방향 그래프일 때 `u → v`만 추가하고, 무방향 그래프일 때는 `v → u`도 함께 추가한다.
- `dfs(int start)`는 재귀 깊이 문제를 피하기 위해 `ArrayDeque`를 명시적인 스택으로 사용했다.
- `bfs(int start)`는 큐에 넣는 시점에 방문 처리하여 같은 정점이 중복으로 추가되는 것을 막았다.
- `shortestPath(int start)`는 거리 배열을 `-1`로 초기화하고, BFS로 정점을 처음 발견했을 때 거리를 기록했다. 가중치가 모두 1이므로 처음 기록한 거리가 최단 거리이다.

### 실제로 주당 몇 시간을 썼는가

학습 시간을 별도로 기록하지 않아 정확한 시간을 산정하기 어렵지만 하루에 한시간에서 한시간 반씩은 진행했는데 중간에 교육 과정 프로젝트를 병행하면서 시간을 많이 할애하지 못해서 아쉽습니다. 후반부부터는 꾸준히 학습할 수 있도록 해야할 것 같습니다!

### 가장 어려웠던 주차와 이유

솔직히 매주 어려웠는데, 항상 어디서 어려움을 느끼냐면 자바에 대한 기본적인 객체 지향적 설계와 관련 용어들이 아직 익숙하지 않아 그냥 기본 중심으로만 이해하려고 했을 때가 많았습니다.

이번주 범위인 람다에서도 함수형 인터페이스부터, 추상형 메서드 등등 ... 아직 익숙하지 않은 부분들이 많아서 기본 부분을 좀 더 꼼꼼하게 봐야할 필요가 있지 않나 싶은데, 꾸준히 공부해서 따라가볼게용!

### 4주 전과 비교해 무엇이 달라졌는가

1주차에는 자바 실행 흐름과 자료구조 선택 자체가 익숙하지 않았고, 학습한 내용을 코드로 옮길 때 어디서 시작해야 할지 정말 어려움이 많았습니다... ㅎ

4주차에는 인접 리스트를 직접 구성하고 DFS, BFS, 최단 거리의 목적에 맞추어 스택, 큐, 거리 배열을 선택할 수 있게 된 것 같습니다~

또한 코드를 작성하는 것에서 끝나지 않고 시간복잡도와 공간복잡도를 분석하고, 재귀와 반복, 인접 행렬과 인접 리스트, 스트림과 반복문처럼 여러 방법의 장단점을 비교하려는 관점이 생긴 것 같아용
