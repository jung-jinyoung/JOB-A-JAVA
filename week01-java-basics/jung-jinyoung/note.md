## 1. 핵심 질문 답변

> 검색한 문장을 붙여넣지 말 것. 본인 문장으로 쓰고, 예시 코드를 곁들이면 좋음.

### Q`String`이 불변인 것이 왜 이득인가? (힌트: 캐싱, 해시, 스레드)
`String`은 한번 만들어지면 내용을 바꿀 수 없다.
> 실습 자료 : [`src/practices.StringCheck.java`](./src/practices/StringCheck.java)  
> <i>리터럴 재사용, new String() 로 비교해본 메모리 차이, == 와 equals() 차이</i>


실습 자료처럼 재대입해도 실제로는 새 문자열을 Heap에 만들고 옮기는 것이지, 기존값을 고치는 것이 아니다.  
이 불변성 덕분에 세 가지 장점이 생긴다. 

1. **캐싱**
문자열 리터럴은 재사용된다(String Constant Pool). 값이 변하지 않아 여러 변수가 같은 문자열을 안전하게 공유할 수 있다.   
만약 가변이었다면, 공유된 값을 한쪽에서 수정하는 순간 그 값을 가리키던 다른 모든 병수가 동시에 **오염**된다.
2. **해시**
`HashMap`의 키로 문자열을 쓸 때 1번 장점인 캐싱으로 보장된 안정성 덕분에 저장 시점과 조회 시점의 해시값이 항상 일치하게 된다.
3. **스레드 안전성** 
마찬가지로 값이 안 바뀌므로 여러 스레드가 동시에 읽어도 안전하다.


### Q2. 반복문 안에서 `s += x`를 10만 번 돌리면 내부적으로 무슨 일이 일어나는가? 시간복잡도는?
`String`은 불변이라 `s += x` 는 매번 기존 내용을 처음부터 끝까지 복사하여 새 문자열을 `Heap`에 만들고 `s`의 주소값만 이동하며 기존 문자열은 버려진다.(GC대상)   

반복이 진행될수록 복사해야 할 길이가 늘어나서 (1번쨰 0글자, 2번째 1글자, ... , 10만번째 99,999글자), 전체 복사량은 `0+1+2+...+(n-1)`, 즉 `n^2`에 비례한다.   

즉 시간 복잡도가 `O(n^2)`가 된다.

해결책은 가변인 `StringBuilder`를 쓰는것이다.
내부에 여유 공간을 가진 배열을 두고 그 자리에 직접 추가하며, 배열이 다 차면 더 큰 배열로 재할당한다.
재할당이 매번 일어나는 것이 아니기 떄문에 전체 시간복잡도는 `O(n)`이 된다.

### Q3.`int` 두 개를 더했는데 음수가 나왔다. 왜 그런가? 어떻게 막는가?

> 실습 자료 : [`src/practices.OverflowCheck.java`](./src/practices/OverflowCheck.java)


먼저 int는 32비트 고정 크기이고 2의 보수 방식으로 값을 표현한다.(범위:약 -21억 ~ 21억)

계산 결과가 이해당 범위를 넘으면 에러나 예외 없이 넘치는 비트가 잘려나가고, 남은 비트를 다시 해석해서 종종 음수가 나온다.

이를 예방하는 방법은 대입받는 변수의 타입이 아니라, 피연산자의 타입을 먼저 확장하는 것이다.

```java
int a;
int b;

long c = a + b; // a+b의 결과가 21억이 넘을 경우 이미 int 범위에서 끝남
long c = (long) a + b; // a를 미리 long으로 캐스팅
```

1. **FastIo 입출력 템플릿 구현**
> 과제 실습 파일 : [FastIo](./src/FastIO.java)

- 어떻게 설계했는가 
  - `BufferedReader`, `StringTokenizer`를 필드로 두고, 토큰이 떨어지면 새로 읽어 교체하는 방식으로 ㄱ후ㅕㄴ

  - 출력은 `BufferedWriter`로 버퍼에 쌓아두고, 프로그램 종료 직전 `flush()`로 한번 호출하도록 설계

2. **성능 측정**
> 과제 실습 파일 : [PerformanceTest](./src/PerformanceTest.java)

- 어떻게 설계했는가 
  - 10만 줄 정수를 담은 `input.txt`를 별도 코드로 생성(`GenerateInput.java`)
  - `System.nanoTime()`으로 Scanner/BufferedReader 각각의 일기 시간을 5회씩 반복 측정 
- 막혔던 지점
  - 자바에서 시간을 측정하는 메서드 조사  

- 실제 성능 결과
  
  | 회차 | Scanner (ms) | BufferedReader (ms) |
  |---|---|---|
  | 1 | 40 | 7 |
  | 2 | 21 | 8 |
  | 3 | 20 | 6 |
  | 4 | 15 | 7 |
  | 5 | 14 | 1 |
  | **평균** | **22.0** | **5.8** |

  - (결론) `BufferedReader`가 `Scanner`보다 빠름
  - (참고) 두 방식 모두 회차가 진행될수록 시간이 줄어드는 경향이 있음

## 5. 아직 모르겠는 것

### 1) 자바의 실행 원리를 흐름대로 잘 설명할 수 있는가. 

JVM이 대략 "바이트코드를 실행해주는 가상의 관리자" 같은 존재라는 것까지는 이해했는데, .java부터 실행까지 전체 흐름을 막힘없이 순서대로 설명하는 건 아직 어렵다. 

특히 JVM이 정확히 무엇을 "관리"하는지(클래스 로딩, 메모리, 실행 자체를 다 포함하는지)가 개념적으로 뭉뚱그려져 있는 상태. 

다음에 흐름 전체를 말로 설명해보는 연습이 필요함.



### 2) 자료구조 선택 감각이 없다 — 언제 무엇을 쓰는지

이번 두 문제에서 배열(`int[]`, `String[]`), `Map`, `StringBuilder`를 썼는데
"이 상황이니까 이걸 쓴다"는 판단이 아니라 학습한 것으로 따라 쓴 것에 가깝다.

특히 헷갈리는 것:
- 배열(`int[]`)과 `ArrayList<Integer>`를 언제 나눠 쓰는지.
  크기를 아는 경우엔 배열, 모르면 리스트로 이해하면 되는지?
- 값을 찾는 상황에서 배열 순회 + `equals` 와 `Map.get()` 중
  크기가 10 정도로 작아도 `Map`을 쓰는 게 맞는지?
- 실무와 코테에서 주로 쓰는 구조가 다른지.
  (코테는 `int[]`를 많이 쓰는 것 같은데, 실무에서도 그런지)
