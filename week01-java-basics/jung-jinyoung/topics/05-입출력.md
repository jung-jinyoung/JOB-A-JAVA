## Week 1 Review — 5주제: 입출력

> 이번 정리는 개념 학습(Scanner/BufferedReader/StringTokenizer/BufferedWriter 원리) 범위까지만 다룹니다. `FastIO` 구현과 성능 측정은 별도 필수 제출 과제로, 아직 진행 전입니다.

### 학습 내용
- `Scanner`가 느린 이유 — 매 호출마다 정규표현식으로 토큰 경계 탐색 + 타입 검사
- `BufferedReader`가 빠른 이유 — 버퍼링(한 번에 큰 단위로 읽어와 메모리에 쌓아둠)과 타입 검사 생략
- `StringTokenizer`로 한 줄을 여러 값으로 분리하는 법과, `split()`과의 차이
- `System.out.println` 반복 호출이 느린 이유와 `BufferedWriter`의 버퍼링 출력 원리


### 이해한 핵심 개념
- `Scanner.nextInt()`는 다음 토큰을 찾아 그 내용이 정수 형식에 맞는지 정규표현식으로 매번 검사한 뒤 변환한다. 이 안전장치(타입 불일치 시 `InputMismatchException`) 덕분에 잘못된 입력을 안전하게 걸러낼 수 있지만, 호출마다 이 검사가 반복돼 비용이 크다.
- `BufferedReader`는 `nextInt()` 같은 타입별 메서드가 없고 `readLine()`으로 한 줄 전체를 `String`으로 가져온다. 대신 입력을 한 글자씩 시스템에 요청하지 않고 **한 번에 큰 단위(기본 8KB)로 미리 읽어와 메모리(버퍼)에 쌓아두고**, 이후 호출은 이 버퍼에서 꺼내오기만 해서 시스템 요청 횟수 자체가 크게 줄어든다.
- `StringTokenizer`는 `split()`처럼 정규표현식을 쓰지 않고 단순 문자 비교로만 문자열을 자르기 때문에 더 가볍다. `hasMoreTokens()`로 남은 토큰이 있는지 확인하고 `nextToken()`으로 하나씩 꺼내는 구조이며, 항상 `String`을 반환하므로 숫자로 쓰려면 `Integer.parseInt()` 등으로 직접 변환해야 한다.
- `System.out.println`을 반복 호출하면 호출할 때마다 운영체제(OS)에 "출력해달라"는 요청(시스템 콜)을 매번 보내는데, 이 요청 자체가 비용이 크다.
- `BufferedWriter`는 `write()` 호출 시 버퍼(메모리)에 쌓아두기만 하고, `flush()`를 호출하는 순간 쌓인 내용을 한 번에 시스템에 요청해 출력한다. `flush()`를 빠뜨리면 버퍼에 쌓인 내용이 출력되지 않은 채 프로그램이 끝나버릴 수 있다는 것을 직접 실행해 확인함.
- 입력(Scanner→BufferedReader)과 출력(println→BufferedWriter) 모두 근본 원리는 같다: **매번 시스템에 요청하는 대신, 모아뒀다가 한 번에 요청**하는 것이 성능 차이의 핵심이다.

### 어려웠던 부분
- `StringTokenizer` 설명 없이 바로 코드로 넘어가서, 개념(비유, 동작 순서)을 다시 짚어야 이해가 됨.
- `BufferedWriter` 부분에서도 코드부터 제시되어, 비전공자 학습 단계에 맞지 않아 개념(등장 배경 → 비유 → 최소 코드) 순서로 다시 설명받음.
- `split()`과 `StringTokenizer`가 둘 다 가능한 방법인데 왜 후자를 관례적으로 쓰는지(정규식 유무에 따른 성능 차이)를 헷갈렸다가 정리함.

### 새롭게 알게 된 Java 특징
- `Scanner`의 기본 구분자는 공백류 문자(스페이스, 탭, 줄바꿈) 전부이며, 줄바꿈만을 기준으로 하지 않는다.
- `StringTokenizer`는 생성자에 구분자 문자를 직접 지정할 수 있다(기본은 공백).
- `BufferedReader`/`BufferedWriter`는 각각 입력/출력에서 같은 원리(버퍼링으로 시스템 요청 횟수 최소화)로 동작한다.
