## .java → .class → JVM 로딩 → 실행

`.java`는 우리가 적는 자바 소스 코드  
`.java`를 javac 컴파일러가 `.class` 파일 (바이트코드)로 만듦  
바이트코드를 JVM이 각 플랫폼에 맞게 기계가 이해할 수 있는 네이티브 코드로 변경함

대충 이런 `.java` 파일을 작성했다고 치자

```java
public int add(int a, int b) {
    return a + b;
}
```

이 파일을 `.class` 파일로 컴파일 후 바이트코드를 뜯어보면 이렇게 생김

```
0: iload_1  
1: iload_2  
2: iadd  
3: ireturn  
```

각 파라미터를 스택에 넣고, 그 2개를 합한 후, 다시 반환해준다는 의미 우리가 아는 Java 코드를 JVM이 알아볼 수 있도록 만드는 과정

이 파일을 JVM을 사용해서 네이티브 코드로 변경하면 대충 이렇게 생김

```
0x00007f8b911a3450: mov    %eax,-0x14(%rbp)  
0x00007f8b911a3453: mov    %edx,-0x18(%rbp)  
0x00007f8b911a3456: mov    -0x14(%rbp),%eax  
0x00007f8b911a3459: add    -0x18(%rbp),%eax  
0x00007f8b911a345c: pop    %rbp  
0x00007f8b911a345d: retq  
```

여기부턴 진짜 기계어 (어셈블리)

왜 이런 구조를 가질까?  
우선 Java는 **"Write Once, Run Anywhere"** 이라는 슬로건을 가지고 있음  
**한번 작성하면 어디서나 작동 가능**한 구조를 만드려고 함 예를 들어, C언어는 컴파일하면 exe 파일이 나오는데 이건 맥북이나 리눅스에서 안돌아감  
OS 마다 기계어를 인식하는 방법이 달라서 그럼

Java에서는 이 문제를 해결하기 위해 바이트코드와 JVM을 만듦  
사용자는 플랫폼에 상관없이 그냥 코드를 짜고, 그 코드를 바이트코드로 컴파일함  
각 플랫폼에서는 그 플랫폼에 맞는 JVM을 설치해두면 모든 바이트코드를 네이티브 코드로 변역해서 실행할 수 있음  
이렇게 컴파일 언어의 장점을 챙기면서 플랫폼에 종속되지도 않는 방법을 사용하는 것

그렇다면 JVM은 어떻게 바이트코드를 네이티브 코드로 만들까?  
이 과정에서 인터프리터와 JIT 컴파일러 라는 것이 모두 사용됨  
인터프리터는 우리가 아는 그대로 코드를 한 줄 한 줄 읽어서 실행함  
컴파일러에 비해 당연히 속도는 떨어질 수 밖에 없음  
그래서 Java에서는 이를 보안하기 위해 JIT 컴파일러 라는 것을 같이 넣어둠  
JIT 컴파일러는 많이 사용되는 바이트코드를 통째로 번역 후 메모리에 저장해버림

바이트코드와 JVM으로 이루어진 구조도 그렇고, JVM 내에서도 인터프리터와 컴파일러를 모두 사용하는 구조를 보니 인터프리터와 컴파일러 각각의 장점만을 사용해보려고 머리 쓴 흔적이 보여서 좋았음

## JVM / JRE / JDK 차이

 - **JVM(Java Virtual Machine)**    
바이트코드를 네이티브 코드로 변환하고 실행하는 핵심 도구  
 - **JRE(Java Runtime Environment)**  
말 그대로 자바를 실행하기 위해 필요한 도구 모음  
JVM과 자바 표준 라이브러리를 포함  
- **JDK(Java Development Kit)**  
자바를 개발하기 위해 필요한 도구 모음  
JRE와 컴파일러 등 여러 도구를 포함  

## 클래스 로더가 하는 일 (개념 수준)  

바이트코드를 네이티브 코드로 번역하기 위해서 `.class` 파일을 JVM 메모리로 올려야 함  
이 역할을 하는 것이 **클래스 로더**  

진짜 JVM 메모리에 올리기만 했으면 따로 이름이 있지도 않겠지  
중요한건 동적 로딩을 지원함  
여기서 동적 로딩이란 그 클래스 필요없으면 올리지 않고 있다가, 필요한 순간 메모리에 올리는 기술  
이로 인해 효율적인 메모리 사용이 가능함
